# Automated Code Quality Report

## Program Overview

Automated Code Quality Report is a web application for submitting a Python file, checking it with Flake8, viewing the findings and a calculated score and optionally downloading a separately auto-fixed copy.

It has three main parts:
- React/Vite Frontend - the submission form, report view and fixed-code view.
- FastAPI Backend - accepts uploads, stores submission records, returns report status and provides an auto-fix endpoint.
- Background Analysis Services - PostgreSQL (stores submissions and reports), Redis and Celery (queue and run analysis) and Docker (runs Flake8 in an isolated container).

The intended input is Python source code. Although the submission API accepts a `language` value, the current frontend sends `python` and the analyzer only runs Flake8 for Python.

### Main Program

1. Enter a Student ID and Assignment ID on the main page. select a `.py` file and submit it.

2. Select a Python file (`.py`) and submit it to the main program.

3. The frontend uploads the file and metadata to the Application Programming Interface (API).

4. The API saves a submission record with a `PENDING` status and queues a background task.

5. The Celery worker changes the status to `PROCESSING`. It runs Flake8 in a temporary Docker container with the source mounted read-only and network access disabled.

6. The frontend checks the API periodically for the result. It shows an error if analysis fails or takes too long.

7. The report page shows the original code, issue locations, diagnostic messages and the score when the analysis finishes.

The main flow is implemented in `App.jsx`, the API routes are in `main.py` and the background task and scoring logic are in `worker.py`.

### Reports & Scoring

The report lists each Flake8 diagnostic with its rule code, line, column, message and category. In the current implementation:

- Rules whose codes start with E are categorized as Convention and cost 2 points each.
- Other Flake8 findings are categorized as Refactor and cost 3 points each.
- The score is 100 - total penalties, rounded to two decimal places and not allowed below 0.

For example, one Convention finding gives a score of 98 while one Refactor finding gives 97.

The current analysis uses Flake8 and does not run a security scanner. Flake8 findings are categorized as Convention or Refactor. The `Warning` and `Security` penalty values in the worker are not assigned to ordinary Flake8 findings.

The current frontend always submits `python`. The API accepts a `language` field, but the worker only runs Flake8 when its value is `python` while other language values currently complete with an empty report and a score of 100. Use Python files for meaningful analysis.

### Auto-Fix

From the results page, **Fix the Python Code** sends the original source to the backend’s auto-fix logic. It can repair some common syntax mistakes, remove unused imports and variables and format code. The fixed source is displayed separately and can be downloaded as a `_fixed.py` file as the upload is not overwritten.

Auto-fix is not a general-purpose code repair tool. It cannot reliably infer what the program was intended to do or fix arbitrary logic errors. If it cannot safely repair a syntax problem, it returns an error instead.

## Project Files and Tests

- `.vscode/` folder[^1] contains workspace settings and a FastAPI debug configuration. The workspace Python interpreter is set to `backend/.venv315/Scripts/python.exe`.
- `backend` folder contains the FastAPI API (`main.py`), database model/configuration (`database.py`), request/response schemas (`schemas.py`), Celery analysis worker and auto-fix implementation (`worker.py`), dependencies (`requirements.txt`) and Flake8 image definition (`Dockerfile.linter`). `backend/.venv315/`[^1] is the local Python environment and is generated during setup.
- `backend/autofix.py` contains the Python `unittest` tests for the auto-fix function. Run them from the `backend` folder with:

```
./.venv315/Scripts/python.exe -m unittest autofix
```

- `frontend` folder contains the Vite/React application. `index.html`, `src/`, `package.json`, `package-lock.json` and `vite.config.js` are frontend source/configuration files. `frontend/node_modules/`[^1] is generated by `npm install` while `frontend/dist/`[^1] is generated by `npm run build` and is not used by the Vite development server.
- `test` folder contains example Python files that can be submitted through the application. They are not the auto-fix unit test suite.

## Step-By-Step Project Startup on Windows with Git Bash

This program requires Docker Desktop, Python 3.15, and Node.js/npm to be installed. Start Docker Desktop first. The backend runs from `backend/.venv315` while the frontend dependencies are managed through npm.

This setup runs five services/processes:
- PostgreSQL in Docker
- Redis in Docker
- Celery Analysis Worker
- FastAPI Backend
- React/Vite Website

Keep the worker, API and frontend running in separate Visual Studio Code terminals while using the app.

### Step 1: Open the Project and Select Git Bash

1. Open the project folder in Visual Studio Code:

```
Automatic Code Quality Report
```

2. Select **Terminal → New Terminal** in Visual Studio Code.

3. Open the terminal profile menu beside the + button and select **Git Bash** if the terminal is not Git Bash.

4. Check that the commands are available:

```
py -3.15 --version
node --version
npm --version
docker --version
```

Python 3.15 may not be installed or available through the Windows Python launcher if `py -3.15` fails. Docker commands also require Docker Desktop to be installed and running.

### Step 2: Create the Python Environment and Install Backend Dependencies

1. Make sure the terminal's current directory is the project root opened in Visual Studio Code. From there, go to the backend folder. Git Bash uses `/c/...` paths for the Windows `C:\...` drive:

```
cd backend
```

2. Create the virtual environment and install the requirements:

```
py -3.15 -m venv .venv315
./.venv315/Scripts/python.exe -m pip install -r requirements.txt
```

The `./` at the start matters in Git Bash. It tells the shell to run the executable in the current folder. You only need to create this environment and install the packages the first time, or after removing the environment or changing dependencies.

3. Check that the environment uses Python 3.15 with:

```
./.venv315/Scripts/python.exe --version
```

Configure Visual Studio Code optionally to use it for Python features:
  1. Open the Command Palette with **Ctrl + Shift + P**
  2. Choose **Python: Select Interpreter**
  3. Select `backend/.venv315/Scripts/python.exe`

### Step 3: Start Docker Desktop and Database Services

1. Start Docker Desktop and wait until it reports that Docker is running.

2. Create and start the PostgreSQL and Redis containers in a Visual Studio Code terminal for the **first time**:

```
docker run -d --name linter-postgres -e POSTGRES_USER=linter_user -e POSTGRES_PASSWORD=linter_password -e POSTGRES_DB=linter_db -p 5432:5432 postgres:17
docker run -d --name linter-redis -p 6379:6379 redis:7
```

3. Use this command if you already created these containers and just need to start them again:

```
docker start linter-postgres linter-redis
```

4. These containers need to keep running while you use the application. PostgreSQL stores submissions and reports while Redis carries work from the API to the Celery worker.

### Step 4: Build the Flake8 Image

The analysis worker runs Flake8 inside a Docker container. Change to the backend folder in a terminal and build the image:

```
cd backend
docker build -f Dockerfile.linter -t alpine-python-linter:latest .
```

The project already includes `Dockerfile.linter`, so you do not need to create it. The linter image and the backend environment both use Python 3.15. Rebuild the `Dockerfile.linter` image before analyzing files again if it changes. The worker starts a fresh container for each analysis, so restarting Celery is not required just to use the rebuilt image.

### Step 5: Start the Celery Worker

Open a **new Visual Studio Code terminal** with **Terminal → New Terminal** and run:

```
cd backend
./.venv315/Scripts/python.exe -m celery -A worker.celery_app worker --pool=solo --loglevel=info
```

Leave this terminal open. The worker receives analysis jobs from Redis and uses Docker to run Flake8.

### Step 6: Start the API Backend

Open another **new Visual Studio Code terminal** with **Terminal → New Terminal** and run:

```
cd backend
./.venv315/Scripts/python.exe -m uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

Leave this terminal open. The API is at `http://127.0.0.1:8000`. Its interactive documentation is at `http://127.0.0.1:8000/docs`.

### Step 7: Install Frontend Packages and Start the Website

Open another **new Visual Studio Code terminal** with **Terminal → New Terminal** and run:

```
cd frontend
npm install
npm run dev -- --host 127.0.0.1 --port 5173
```

Run `npm install` the first time or if frontend dependencies are missing. Leave this terminal open too. The website should be available at `http://127.0.0.1:5173/`.

### Step 8: Submit a Python File

1. Open `http://127.0.0.1:5173/` in your browser.

2. Enter a Student ID and Assignment ID.

3. Select a Python file (`.py`).

4. Click **Analyze File** and wait for the results.

5. The report shows the score and Flake8 findings. **Fix the Python Code** attempts supported repairs and offers the result as a separate download.

All service terminals and Docker Desktop must remain running during use.

## Step-By-Step Project Stopping on Windows with Git Bash

### Step 1: Stop the Frontend Terminal

Press **Ctrl + C** in the frontend terminal.

### Step 2: Stop the API Terminal

Press **Ctrl + C** in the API terminal.

### Step 3: Stop the Celery Worker Terminal

Press **Ctrl + C** in the Celery worker terminal.

### Step 4: Stop the Database Containers

1. Stop the PostgreSQL and Redis containers without deleting their data with:

```
docker stop linter-postgres linter-redis
```

2. Run this if you want to remove the containers:

```
docker rm linter-postgres linter-redis
```

Removing the conatiners is not part of normal shutdown because the PostgreSQL image uses an anonymous data volume. Removing a container without `-v` can leave its volume behind, but the next `docker run` creates a new container with a new volume and will not automatically reconnect to the old data. Stop and start the existing container instead to preserve and continue using the existing database. Do not add `-v` when removing containers unless you intend to delete their associated volumes.

3. Run this if you want to remove the linter image:

```
docker rmi alpine-python-linter:latest
```

## Step-By-Step Project Restarting on Windows with Git Bash

### Step 1: Start the Docker Desktop and Database Containers

1. Start Docker Desktop and wait until it reports that Docker is running.

2. Recreate the Python environment by following Step 2 of **Project Startup on Windows with Git Bash** if it was removed. Rebuild the `Dockerfile.linter` image by following Step 4 of **Project Startup on Windows with Git Bash** if the linter image was removed or changed. Install the backend dependencies in `.venv315` with the `pip` command in Step 2 of **Project Startup on Windows with Git Bash** if it changed and restart the API and worker.

3. Start the PostgreSQL and Redis containers with this command if they still exist:

```
docker start linter-postgres linter-redis
```

Recreate the containers by running the two `docker run` commands in Step 3 of **Step-By-Step Project Startup on Windows with Git Bash** instead if the containers were removed. Starting existing containers preserves their stored database data while newly created containers start with a new database.

### Step 2: Start the Celery Worker

Open a **new Visual Studio Code terminal** with **Terminal → New Terminal** and run:

```
cd backend
./.venv315/Scripts/python.exe -m celery -A worker.celery_app worker --pool=solo --loglevel=info
```

Leave this terminal open. The worker receives analysis jobs from Redis and uses Docker to run Flake8.

### Step 3: Start the API Backend

Open another **new Visual Studio Code terminal** with **Terminal → New Terminal** and run:

```
cd backend
./.venv315/Scripts/python.exe -m uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

Leave this terminal open. The API is at `http://127.0.0.1:8000`. Its interactive documentation is at `http://127.0.0.1:8000/docs`.

### Step 4: Install Frontend Packages and Start the Website

Run `npm install` first in the `frontend` folder if the frontend dependencies are missing as shown in Step 7 of **Project Startup on Windows with Git Bash**. Then, open another **new Visual Studio Code terminal** with **Terminal → New Terminal** and run:

## Changes To The Running Programs, Its Effects & Its Solutions

The effect of a code change depends on which service owns the changed file. Use this guide to help you with the project’s current startup commands:

| **Changes** | **Effects While Running** | **Solutions** |
| --- | --- | --- |
| **Frontend Files (`frontend/src/`)** | Vite usually updates the browser automatically when you save (hot reload) | Usually nothing, just check the browser if it does not update |
| **Frontend configuration/Dependencies (`vite.config.js`, `package.json`)** | Vite may restart, but dependency changes are not installed automatically | Stop the frontend with **Ctrl + C** and after dependency changes, run `npm install` in `frontend`, then restart Vite |
| **Backend API Files (`main.py`, `schemas.py`, `database.py`)** | Uvicorn's `--reload` option restarts the API when it detects Python changes | Usually no manual restart, just check the API terminal for startup errors |
| **Analysis Worker Code (`worker.py`)** | Celery worker runs as a separate process while Uvicorn's reload does not reload it | Stop the worker with **Ctrl + C**, then run its startup command again |
| **Linter Dockerfile (`Dockerfile.linter`)** | Editing the Dockerfile does not change an image that has already been built | Rebuild the image before testing and Celery worker does not need restarting just for this change because it starts a fresh container for each analysis |
| **Backend dependencies (`requirements.txt`)** | Running Python processes keep using their currently installed packages | Run `./.venv315/Scripts/python.exe -m pip install -r requirements.txt` from `backend`, then restart the API and worker |
| **Database Model/Schema** | Editing model definitions does not automatically update existing PostgreSQL tables | Apply a migration or make the required database schema update |
| **Python File Submitted For Analysis** | A submission already being processed uses the uploaded copy | Submit the changed file again to analyze the new version |

[^1]: Not shown in GitHub repository
